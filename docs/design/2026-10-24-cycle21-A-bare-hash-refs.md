# cycle-21 A 设计记录 — 正文/指针里「裸写」提交哈希的机器校验

> 日期：2026-10-24 ｜ step A 提交 `de64aca`；B 增量 `a3681a4`（architect-skills：TES-17 + DOC-08）
> 基线 1604 / 78.73 → **1608 / 78.73**（+4 用例，coverage 持平）

## 1. 触发

用户在 cycle-20 之后再次追问：「任何照链取证的 agent（回溯代码、写交接、做归因）都会拿到错哈希，而错哈希会被当成事实一路传递。这个修复了嘛？」

不口头回答，直接取证。三仓交叉（sloth-loop / legacy `sloth-loop` / architect-skills）复查 cycle-20 的守卫覆盖面。

## 2. 复查结论：仍有盲区

cycle-20 的 `phantom_hash_problems` 只提取两类 token：**反引号哈希**与**箭头链里的哈希**。于是：

- GRAND-LOOP 的**唤醒指针路径行**在散文里裸写提交哈希：`HEAD 1fb4846 … 362e479/af5cd11`；
- status registry 的**提交列**同样裸写：`766209c/24be2bb/56b1b6e`，以及多行 `->` 长链。

全仓实测：**79 个唯一裸 token（179 处）**，此前**从未被任何守卫看过**。

## 3. 取证结果

按「裸 token 是否能在已知仓解析」逐一定位：

- **真错 0 个**（当前语料干净）。
- 但发现**一个新类别**：`2ee2239`（status 13 / cycle-1 行 「TencentDB@2ee2239」）在三仓都解析不出——它是**外部源仓** `TencentDB-Agent-Memory` 的真实提交（`SOURCE.md` 登记的源版本 pin）。**若不登记该 checkout，加宽扫描会把真 pin 误判为幽灵**。

## 4. 修复（step A：commit `de64aca`）

新增 `_bare_git_context_tokens`，并入 `phantom_hash_problems`：

- **共现门控**：裸 token **仅当同一行已含至少一个可解析提交引用**时才视为提交引用。这排除了「字母全落在 a–f 的普通英文单词」（7 位以上）这类噪声——**裸扫必然误报**；实测当前语料 0 误报。
- **摘要标签**：带 `md5=` / `sha256:` 等标签的行整体跳过（如 `docs/LOOP-ESSENCE-AND-LEARNINGS.md` 里的重测 md5）。
- **纯数字 token 仍排除**：`20261014` 这类日期会与真哈希同现于 git 上下文行（实测），保留排除。
- **外部源仓 pin**：新增 `EXT_SOURCE_REPOS`；checkout 存在时并入已知仓，`2ee2239` 因此合法解析。

## 5. 自证

- 向仓库根放一个含裸「不存在的 7 位 token」（同行含真哈希）的未跟踪 `.md` → 守卫**立刻 FAIL**，报 `bare ... resolves in no known repo`；删除后恢复 0 违规。
- 语料统计自证：规则实际检查 **179 处 / 77 唯一 / 61 篇**，非空转。
- +4 用例：裸哈希被抓；无 git 上下文的全 hex 英文词不误报；摘要行跳过；外部源仓 pin 解析。

## 6. 边界（诚实记录）

- 共现门控意味着**独占一行的裸哈希仍不受保护**（一行只有一个裸 token 时无法判定它是不是提交引用）；这是与「全 hex 英文词误报」不可兼得的取舍。
- 纯数字 7 位哈希（如 `3230295`）仍会漏（与日期误报不可兼得）。
- 跨仓箭头只做存在性。
