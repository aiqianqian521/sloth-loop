# cycle-27 A 设计说明 · 识别器的字母表不得窄于它审计的现实

> 结论：2026-10-24。本循环走 A→B→C→D。step A 提交 `a281839`，B 轮 `1222959`（architect-skills，TES-23 + DOC-14）。
> 实况 1632 / 78.73 → **1642 / 78.73**（+10 用例；coverage 持平）。

## 1. 背景

cycle-26 C/D 给下一位留下了一条登记候选：

> **（候选，未机器化）哈希旁的轮次标注无人校验**：`CLAUDE.md` 里「HEAD `<hash>`（cycle-16 A：…）」这半句自 cycle-16 C/D 写下后从未随哈希更新——哈希被门禁机器校验，紧挨它的那句轮次描述没有。

本轮去收这条候选，结果**没有先找到标注，先找到了引擎**：`tests/test_wake_pointer_chain.py` 里三处解析器各自硬编码了 7 位哈希。

| 解析器 | 用途 | 旧口径 |
|---|---|---|
| `ENTRY_RE` | 提交链条目 `hash`(cycle-N …) | `[0-9a-f]{7}` + ASCII `(` |
| `HEAD_RE` | 唤醒指针 `代码 head `hash`` | `[0-9a-f]{7}` |
| `CLAIM_RE` | 全仓哈希声明扫描 | `[0-9a-f]{7}` + ASCII `(` 紧贴反引号 |

而**幽灵哈希规则**（cycle-20~22）早已采用 `[0-9a-f]{7,40}`。同一个仓库里，同一类引用的识别口径**不一致**，而且都窄于幽灵规则——这就是本轮的真缺口。

## 2. 发现（可复现证据）

1. **静默丢弃（最严重）**：把提交链里任意一条条目的哈希改成**同一提交的 8 位写法**（仍可解析），旧 `ENTRY_RE` 直接**看不见**该条目：

   - `chain_entries` 49 → **48**；
   - 而 `MIN_ENTRIES = 20` 的下限断言**仍然通过**，`chain_violations()` 返回 `[]`；
   - 即：一条记录被丢掉，守卫报「无问题」而不是报红。**假阴性比误报危险**——误报会被人打回，漏报会被当成事实。
2. **口径窄 → 全仓漏扫**：`docs/flow/2026-09-05-grand-loop-task.md` 里写的是

   > …HEAD `64de89b`（cycle-1 A→B→C→D 闭合；动态状态见 …），…

   用的是**全角括号**。旧 `CLAIM_RE` 要求反引号后**紧跟 ASCII `(`**，因此这条声明 **0 个识别器**能看见。全仓实测：旧口径 49 条 vs 放宽后 50 条（唯一多出来的就是它）。
3. **看见也会误报**：`64de89b` 是 **legacy 仓 `sloth-loop`** 的提交（分支 `codex/w0-w2`），而 `claim_problems` 只在本仓解析——口径一放宽，这条就会被报成「幽灵」。**只看本仓 = 把合法跨仓引用变成假阳性。**

三条证据共同指向一句话：**守卫的识别口径就是守卫自身的边界**。

## 3. 方案（step A，commit `a281839`）

1. **单一口径**：新增 `HASH_SRC = r"[0-9a-f]{7,40}"`，由 `ENTRY_RE` / `HEAD_RE` / `CLAIM_RE` **共用**；另加 `LPAREN_CLASS`（ASCII 与全角左括号）。同族引用识别不再各写各的长度。
2. **`CLAIM_RE` 放宽**：`[ \t]*` + 全 / 半角括号 + 可选空白，覆盖「反引号哈希 + 括号 + cycle-N」的全部现实写法。
3. **跨来源解析**：`claim_problems` 在本仓解析失败时，改走 `_resolve_any(h, _known_repos())`（本仓 / legacy / 姊妹仓 / 外部源 pin），之后才判幽灵。
4. **head 指针按提交比较**：`chain_violations` 不再比对**字符串**，而是判断两侧是否互为**前缀**——git 缩写是唯一前缀，因此「同一提交的不同长度写法」合法，**非前缀**才是真漂移（负控：换成另一条链条目的哈希仍必须 FAIL）。
5. **保留缺陷见证**：`NARROW_CLAIM_RE` / `NARROW_ENTRY_RE` / `NARROW_HEAD_RE` 三份旧口径副本留在测试里，专门用来断言「放宽确实多看见了东西」。

`tests/test_wake_pointer_chain.py`（34 → 44，+10）：

- 三个识别器共用字母表（行为断言：8 位哈希必须被三者都看见，且三个 `NARROW_*` 都看不见）；
- 放宽对**已发布文档的判定零变化**（逐模式 `NARROW == WIDE`）；
- 链条目更长哈希**保住条数**（并断言旧口径少一条——红色证据内建）；
- 全角括号 / 括号前空白两种**负控**（改坏即必须 FAIL，且旧口径看不见）；
- 全仓「窄 ⊂ 宽」自证 + 被救回的那条记录**点名**（`docs/flow/2026-09-05-grand-loop-task.md`）；
- 被固定的 legacy 声明：宽口径命中、窄口径 0 命中、`claim_problems` 必须**不报**（跨仓解析）；
- 未知哈希仍必须报「不存在」（跨仓放宽没有把幽灵规则一起放掉）；
- head 指针接受更长写法（旧口径直接定位失败）、换成另一条链条目仍必须 FAIL。

## 4. 验证

- **红色在前**：把三个识别器还原成旧口径、同一批测试 → **7 failed / 37 passed**（另 3 条是「不误报 / 仍能抓到真错」的对照，两种状态下都应绿）；恢复后 44 passed；
- `pytest tests sloth_engine/tests -q` → **1642 passed / 1 xfailed / coverage 78.73%**（1632 → 1642）；
- `run_gate.py --all` → PASS（baseline-vs-measured / docs-baseline / orphan-mechanisms 全 OK）；
- architect-skills：`validate-contracts.mjs` → 19 atom / 0 错 / 0 警、`run-l1-tests.mjs` → 32 passed、跨仓账本扫描 unexplained 0 / exit 0。

## 5. 残余风险

- `ENTRY_RE` 仍要求链条目用 **ASCII 括号**：全角括号的链条目会被静默跳过（同族缺陷的下一面，未机器化）；
- `HEAD_RE` 仍要求固定前缀「代码 head 」；
- 轮次标注只在「反引号哈希 + 括号 + cycle-N」形态下被校验：`HEAD \`hash\`，cycle-25 A`（逗号）/ 破折号 / 空格分隔的写法仍不可见 —— cycle-26 候选只是**部分**闭合，其余形态已登记；
- 跨仓解析放宽后，本仓打错的哈希若恰好命中别仓某提交（legacy 仓 2300+ 提交）即不再报幽灵：**用覆盖换精度**，刻意保留；
- 8 位前缀在极端情况下可能不再唯一（git 只保证 `%h` 的 7 位唯一性）；本轮把所有长写法都按「可解析」处理，未做唯一性再校验。
